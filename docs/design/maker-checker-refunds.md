# تصميم: مبدأ الأربع عيون على استردادات الضمان — P2 (backlog بند 30)

**الحالة:** تصميم للمراجعة قبل التنفيذ (جلسة مراجعة العمل تُحكِّم). كُتب أثناء انتظار soak الساعة 2026-08-21.

## المشكلة

`POST /v1/admin/escrow/:id/refund` اليوم خطوة واحدة: موظف منصة واحد + سبب مكتوب + سجل تدقيق.
المال يخرج فعلياً (قيد دفتر + استرداد PSP) بقرار فردي — وثّقناه قصداً في الخطوة 15 كحلّ مؤقت للتجربة،
لكن المال الحقيقي قبل الإطلاق يحتاج عينين ثانيتين على كل استرداد.

## المبدأ

**الطالب لا يعتمد، والمعتمد لا يطلب.** أي استرداد يمرّ بحالتين: `requested` (صانع القرار الأول)
ثم `approved|rejected` (المُدقّق — موظف آخر). القيد المالي واسترداد الـ PSP لا يحدثان إلا عند الاعتماد،
داخل معاملة الاعتماد نفسها. لا مسار سريعاً يتجاوز الخطوتين — حتى super_admin يحتاج شخصاً ثانياً.

## المخطط (تعديل واحد على schema.sql + Prisma معاً — قاعدة §5.7)

جدول جديد `admin_approvals` — عام بما يكفي ليخدم لاحقاً أي إجراء حساس آخر (تجميد جماعي، تعديل نسب):

```sql
CREATE TABLE admin_approvals (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  action          varchar(60)  NOT NULL,              -- 'escrow.refund' الآن؛ الإجراء مفتوح للمستقبل
  entity_type     varchar(40)  NOT NULL,              -- 'escrow_hold'
  entity_id       uuid         NOT NULL,
  payload         jsonb        NOT NULL,              -- {amount, reason_ar} كما طلبها الصانع، تُنفَّذ حرفياً
  status          varchar(16)  NOT NULL DEFAULT 'requested',  -- requested | approved | rejected | expired
  requested_by    uuid         NOT NULL REFERENCES users(id),
  requested_at    timestamptz  NOT NULL DEFAULT now(),
  decided_by      uuid         REFERENCES users(id),
  decided_at      timestamptz,
  decision_reason_ar text,
  expires_at      timestamptz  NOT NULL,              -- المدة من platform_settings (approvals.expiry_hours، افتراضي 72) لا ثابتاً في الكود
  -- شرط الشخصين ينحصر في الاعتماد وحده: الطالب يستطيع سحب/رفض طلبه هو (خطأ مطبعي لا يحتاج زميلاً)،
  -- لكن لا أحد يعتمد ما طلبه بنفسه.
  CONSTRAINT approvals_two_people CHECK (status <> 'approved' OR decided_by IS NULL OR decided_by <> requested_by)
);
CREATE INDEX idx_admin_approvals_pending ON admin_approvals (action, status) WHERE status = 'requested';
CREATE UNIQUE INDEX uq_admin_approvals_open_entity ON admin_approvals (action, entity_id) WHERE status = 'requested';
```

قيد `two_people` في القاعدة نفسها لا في الكود فقط — نفس فلسفة الدفتر (الـ DB يعيد التحقق).
الفهرس الفريد الجزئي يمنع طلبين مفتوحين على نفس الحجز.

## تدفق الـ API

| نقطة | من | ماذا |
|---|---|---|
| `POST /v1/admin/escrow/:id/refund` | أدوار المالية في المنصة | لم تعد تنفّذ: تنشئ طلب اعتماد (`requested`) وتعيد 202 مع `approval_id`. Idempotent على الحجز المفتوح |
| `GET /v1/admin/approvals?status=requested` | طاقم المنصة | صندوق «بانتظار الاعتماد» للوحة |
| `POST /v1/admin/approvals/:id/approve` | موظف **غير** الطالب + سبب | ينفّذ الاسترداد الحالي حرفياً (`EscrowUseCases.adminRefund` الحالية تصبح private وتُستدعى من هنا) في نفس المعاملة، ثم `approved` |
| `POST /v1/admin/approvals/:id/reject` | أي موظف مالية **بمن فيهم الطالب** (سحب) + سبب | يغلق الطلب بلا أثر مالي |

- الحجز يبقى قابلاً للتجميد/التحرير العادي أثناء طلب معلّق؟ **لا**: طلب استرداد مفتوح يجمّد
  التحرير التلقائي لنفس الحجز (نضيف شرط `NOT EXISTS (approval requested)` في مهمة auto-release —
  نفس نمط تخطي المجمّد).
- **معاملة الاعتماد تعيد التحقق لحظة التنفيذ** — الحمولة تتقادم: حالة الحجز ما زالت تسمح بالاسترداد،
  والمتبقي (`amount - refunded`) ≥ المبلغ المطلوب. إن تغيّر الوضع منذ الطلب (تحرير يدوي، تجميد نزاع،
  استرداد جزئي آخر) يُرفض الاعتماد بسبب واضح ويبقى الطلب مفتوحاً للقرار.
- كل خطوة تكتب `audit_log` (طلب، اعتماد، رفض، انتهاء) بنفس كاتب السلسلة الحالي.
- إشعار داخلي لبقية طاقم المالية عند فتح طلب (قالب موجود النمط).
- مهمة `LeaderLock` يومية تُعلّم المنتهي `expired`.

## ما لا يتغير

- استردادات **قرارات النزاعات** (`resolve`) تبقى كما هي: قرار النزاع نفسه هو الاعتماد الثاني
  (فتحه طرف، وقرره موظف) — إقحام موافقة ثالثة يضاعف البيروقراطية بلا أمان إضافي.
- استرداد داخل معاملة القرار كما هو (`decisionAmounts` يحرس المدى).
- **شرطا التحكيم على الاستثناء** (جلسة المراجعة): (أ) الآن — قرار نزاع يحرك مالاً يُشعر بقية طاقم
  المالية فور صدوره (رؤية جماعية بعدية بلا بوابة)؛ (ب) بعد التجربة — قرار نزاع يتجاوز استردادُه عتبة
  `platform_settings` (مقترح 5000 ر.س) يمر عبر `admin_approvals` نفسه (بند backlog يُسجَّل مع التنفيذ).

## الاختبارات (منها يبدأ التنفيذ)

1. الطلب لا يحرك مالاً: بعد 202 لا قيد ولا PSP ولا تغيير حالة حجز.
2. الطالب لا يستطيع اعتماد طلبه (403 + قيد الـ DB يرفض لو التُفّ على الكود).
3. موظف ثانٍ يعتمد → قيد متوازن + PSP mock + حالة الحجز، كله في معاملة واحدة؛ imbalance = 0.00.
4. الرفض يغلق بلا أثر؛ طلب ثانٍ على نفس الحجز أثناء المفتوح → 409.
5. auto-release يتخطى حجزاً عليه طلب استرداد مفتوح.
6. انتهاء المدة (من الإعدادات) يُعلّم `expired` ويعيد الحجز لمساره الطبيعي.
7. **تقادم الحمولة**: طلب على حجز حُرّر/جُمّد/استُرد جزئياً بعد الطلب → الاعتماد يُرفض بسبب واضح، لا مال يتحرك.
8. الطالب يسحب طلبه هو → مقبول؛ الطالب يعتمد طلبه هو → 403 والقاعدة ترفض حتى لو التُفّ على الكود.
