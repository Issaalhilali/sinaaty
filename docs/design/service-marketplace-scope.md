# نطاق: سوق طلبات الإصلاح + مكان القطعة — توجيه المالك 2026-08-22

**التوجيه نصاً:** (1) العميل يدرج مشكلته → الورش القريبة تدرسها وترد بتحليل وسعر أو جاهزية → يقارن
ويقبل؛ (2) طالب القطعة يعرف أنها موجودة وسعرها النهائي **وأين هي**؛ (3) العميل يتحكم بنطاق البحث.
روح التوجيه: **حل علاقة العميل بالمنطقة الصناعية** — لا يعرف أي ورشة يقصد، ولا أين القطعة، ويريد
التحكم بمدى بحثه. الأبواب الثلاثة أبواب ثقة قبل أن تكون مزايا.

**التقسيم:** API = الجلسة الرئيسية (بدأت: `service_requests/recipients/offers` على منوال مزاد القطع
المثبت + المدينة/المسافة في عروض القطع وfit). الشاشات = sinaaty-d0 وفق هذه الوثيقة. التحكيم
والقبول = جلسة المراجعة. **العقد النهائي للـ API يصل قبل تجميد هذه الوثيقة** — البنية أدناه على
منوال المزاد القائم وتُصحَّح عليه.

---

## 1) شاشات سوق الإصلاح (mobile — sinaaty-d0)

خلف علم جديد `service_marketplace` (يُضاف إلى KNOWN_FLAGS — نقطة للجلسة الرئيسية).

### أ. العميل — «أصلح سيارتي» في تبويب اطلب
- خيار ثالث في `RequestHubScreen` (المصفوفة الحالية: قطعة/سطحة): **«أصلح سيارتي»**.
- ورقة الطلب (على قالب ورقة القطعة حرفياً): اختيار السيارة → وصف المشكلة نصاً (+صور عبر presign
  القائم؛ الصورة تغني عن ألف كلمة تشخيصية) → **شريحة النطاق** (10/25/50 كم — تحكم المالك نقطة 3،
  نفس `radius_km` القائم في الـ API) → نافذة الاستقبال.
- الطلب المفتوح يظهر في قائمة «طلباتي» القائمة نفسها.

### ب. العميل — شاشة مقارنة العروض
على قالب شاشة عروض القطع (`sortedForCompare` + `bidHighlights` سابقةً):
- كل عرض بطاقة: اسم الورشة + تقييمها ★ + **المسافة** («٧ كم — الصناعية الثانية») + سطر التحليل
  الذي كتبته الورشة + السعر (أو «معاينة مجانية — متوفرون اليوم») + شارة «سبق تعاملك معها» إن وجدت.
- الترتيب بحُجّته الظاهرة: الأرخص / الأقرب / الأعلى تقييماً / الأسرع موعداً — لماذا يفوز كل عرض،
  لا قائمة صماء.
- **القبول = أمر عمل** في نفس المعاملة (الـ API يتكفل) → تهبط على شاشة الأمر القائمة، والمسار
  القانوني القائم كله (فحص → اعتماد موقّع → دفع بضمان) يسري بلا أي جديد. جملة الشاشة:
  «السعر النهائي يُعتمد بعد الفحص وبتوقيعك — لا مفاجآت».

### ج. الورشة — «طلبات قريبة» في تبويب اليوم
- SealCard في أعلى Today (نمط بطاقة hot-request القائمة عند الموردين): «3 طلبات إصلاح قريبة» →
  قائمة → تفاصيل الطلب (الوصف والصور والسيارة والمسافة) → ورقة الرد: سطر تحليل (إلزامي — هو ما
  يميز العرض عن رقم أصم) + سعر تقديري **أو** «معاينة مجانية» + موعد متاح.

### معايير القبول (mobile)
1. اختبار التدفق كاملاً: طلب بعلم مفعّل → عرضان بحُجّتين مختلفتين → قبول → أمر عمل ظاهر للعميل.
2. علم `service_marketplace` مطفأ ⇒ خيار «أصلح سيارتي» وصندوق «طلبات قريبة» غائبان كلياً.
3. golden لشاشة المقارنة (فاتح/داكن RTL) — المسافة والتقييم والحُجّة ظاهرة.
4. لا حساب مسافات في العميل — المسافة تأتي من الـ API نصاً وأرقاماً.

## 2) مكان القطعة (mobile — تعديلان صغيران على شاشات قائمة)
- بطاقة عرض المزاد وبطاقة عرض fit بالـVIN تكسبان سطراً: **«المدينة · N كم»** (+«استلام من المحل»
  حيث يتيحه العرض) — الحقول من إضافة الجلسة الرئيسية للمسافة في الاستجابتين.
- «الأقرب» ينضم إلى حُجج `bidHighlights` القائمة.
- **قبول:** المسافة ظاهرة في المقارنتين؛ عرض بلا إحداثيات لا يكسر الصف (يظهر بلا سطر المكان).

## 3) العقد المبدئي للـ API (حُكّم 2026-08-22 — الوثيقة مجمَّدة عليه؛ النهائي مع الدفع)

- `POST /v1/service-requests` `{vehicle_id?, title_ar, description_ar?, lat, lng, address_hint?, radius_km(2–150, افتراضي 15), preferred_time(now|today|this_week), media_ids?, expires_minutes?}` → 201 `{id, number: SR-…, recipients_notified}`
- `GET /v1/service-requests?mine=true` (عميل) | `?nearby=true` (ورشة)
- `GET /v1/service-requests/:id` — للعميل: العروض مرتبة مع `badges {cheapest, fastest, previously_used}` و**المسافة نصاً جاهزاً** («حي الصناعية — 4.2 كم»)؛ للورشة: الطلب + عرضها هي فقط. ⟵ **الحُجج والمسافة تصل جاهزة — لا حساب في العميل.**
- `PUT /v1/service-requests/:id/offer` (ورشة، upsert) `{offer_type: estimate|free_inspection, diagnosis_ar?, price_min?, price_max?, availability, available_at?, eta_note_ar?}` — `free_inspection` بلا أسعار
- `POST /v1/service-requests/:id/accept {offer_id}` → أمر عمل draft؛ البنود والسعر النهائي على المسار القانوني القائم
- `POST /v1/service-requests/:id/widen {radius_km}` (أكبر من الحالي فقط) · `/cancel`
- Realtime: `service-request:{id}` (offer/accepted/widened) · العلم `service_marketplace` في KNOWN_FLAGS

**انعكاسات على الشاشات أعلاه:** ورقة الطلب تضيف «متى؟» (الآن/اليوم/هذا الأسبوع = `preferred_time`)
وشريحة النطاق ضمن 2–150 (افتراضي 15)؛ بطاقة العرض تعرض السعر نطاقاً «من X إلى Y» أو
«معاينة مجانية»، والحُجج من `badges` كما تصل.

## 4) العصف — الحصيلة المحكَّمة

**قُبلت الأربعة** ودخل الأولان المخطط مباشرة (`offer_type`، `available_at`):
- **«معاينة مجانية» كنوع عرض صريح** لا سعراً صفرياً — أصدق تمثيلاً لواقع الورش (كثير منها لا يسعّر
  قبل الفحص) ويملأ السوق عروضاً بدل صمت الورش المترددة.
- **موعد التوفر في العرض** («اليوم 4 عصراً») — الجاهزية نصف قرار العميل في الإصلاح، بعكس القطع.
- **شارة «سبق تعاملك معها»** — من تاريخ أوامر العميل نفسه، بلا أي بنية جديدة.
- **«وسّع النطاق» بنقرة عند قلة العروض** — طلب بلا عروض بعد نصف النافذة يعرض زر «وسّع إلى 100 كم»
  (تحكم المالك نقطة 3 في اتجاهه الثاني).

مؤجلة إلى backlog (تكسر البساطة الآن أو تحتاج بنية):
- خريطة العروض (نص المسافة يكفي التجربة؛ الخريطة مع تتبع السطحة لاحقاً).
- وصف المشكلة صوتاً عبر وحدة voice (تنتظر مزود الكلام أصلاً — بند قائم).
- مطابقة تخصصات الورشة تلقائياً على نص المشكلة (تحتاج تصنيفاً؛ التوزيع الجغرافي يكفي الآن).

## 5) فروق العقد النهائي (دفعة الـ API `9f27360` — مقبولة 2026-08-22)

- `accept` يعيد `work_order_id` مستوى أول **و** كائن `work_order {id, number, status}`.
- الورشة ترى **عرضها فقط** في `offers` — مثبت بالاختبار (الطول 1 دائماً).
- **أسماء حقول المكان الموحدة** في عروض المزاد ونتائج fit: `supplier_city` · `supplier_district` ·
  `distance_km` · `where_text` (نص جاهز «حي/مدينة — X.X كم»). في عروض السوق على مستوى العرض:
  `city/district/distanceKm/where_text` + `orgNameAr/ratingAvg/ratingCount/previouslyUsed` و`badges`.
- زيادتان: `offers_count` للعميل و`media_ids` للصور؛ وقناة realtime `service-request:{id}`
  (offer/accepted/widened/cancelled) بحارس وصول: الطالب وورش التوزيع فقط.
