# منجز / تقدير — تقارير الحوادث والتقييم (Accident reports)

> **الحالة: افتراض غير مؤكَّد.** الجهة الفعلية وواجهتها البرمجية لم تُؤكَّد بعد (مخاطرة **R3** في `docs/01-PRD.md`).
> ما هو مكتوب هنا هو **العقد الذي بنينا عليه**، ويقابله مُحاكٍ (mock) فقط. لا يوجد adapter حقيقي، والوحدة **ترفض الإقلاع**
> إذا ضُبط `INTEGRATION_ACCIDENTS=live` — أفضل من ادّعاء تكامل لم نره.

## لماذا نحتاجه

الورشة اليوم تُعيد كتابة قائمة الأضرار من ورقة المُقيِّم، والعميل لا يعرف كم يدفع من جيبه إلا عند التسليم. الربط يحلّ الاثنين:

| ما يصل من المزوّد | ما نصنعه منه |
|---|---|
| قائمة الأضرار (قطعة + شدّة + إجراء) | بنود مقترحة لأمر العمل (`suggested_items`) — الورشة تراجع وتُسعّر |
| المبلغ المعتمد + التحمّل + نسبة الخطأ | «المتوقع عليك» للعميل قبل بدء العمل |
| رقم البلاغ | حدث في سجل السيارة (Car Passport) يراه المشتري لاحقاً |
| تسجيل تقرير الإصلاح | إغلاق الملف لدى المزوّد بعد انتهاء الإصلاح (FR-WO-10) |

## المنفذ (Port)

`apps/api/src/modules/accidents/application/ports/accident-reports.port.ts`

```ts
fetchByRef(externalRef, hint?: { vin, plate }): Promise<ProviderAccidentReport | null>
submitRepairReport(s: RepairSubmission): Promise<{ submissionRef, acceptedAt }>
```

**الافتراضات التعاقدية** (يجب التحقق منها عند توقيع الاتفاقية):

1. **البحث برقم البلاغ** متاح للورشة المرخّصة بعد موافقة العميل. لو تطلّبت الجهة موافقة صريحة لكل استعلام، تُضاف خطوة
   تفويض عبر نفاذ قبل `fetchByRef` — يتغيّر الـ adapter فقط.
2. **رقم غير معروف ⇒ نتيجة فارغة** لا خطأ. رقم يكتبه مستشار الخدمة خطأً حالة عادية، ويُرد عليها 404 برسالة عربية.
3. **الحالات**: `reported → under_assessment → assessed → approved | rejected → closed`. نُخزّنها كما هي في
   `accident_report_status`، ولا نسمح بتسجيل تقرير الإصلاح قبل `assessed` (لا توجد أرقام قبلها).
4. **المبالغ نصوص** بخانتين عشريتين (`"4250.00"`)، والنِسب مئوية نصّية. لا أعداد عشرية عائمة (CLAUDE.md §5.1).
5. **`submitRepairReport` مُتَعادِلة (idempotent)** على (رقم البلاغ، رقم أمر العمل): التكرار يعيد نفس `submissionRef`
   ولا يفتح ملفاً ثانياً. نحفظ المرجع في `accident_reports.repair_submission_ref` ونمنع الإرسال المكرر من طرفنا أيضاً.
6. **لا PII في السجلّات**: نحفظ `raw` بعد التنقية، وأسماء الأطراف الأخرى في الحادث لا تُخزَّن إطلاقاً.

## المُحاكي (mock)

`infrastructure/monjez/monjez.mock.adapter.ts` — حتمي: نفس الرقم يعطي نفس التقرير دائماً (مشتق من SHA-256 للرقم).
حالات مفروضة عبر الرقم نفسه:

| الرقم | الناتج |
|---|---|
| `ACC-…` | تقرير مُقيَّم أو معتمد، بأضرار ومبالغ |
| `ACC-…PEND…` | `under_assessment` بلا مبالغ — تسجيل الإصلاح مرفوض |
| `ACC-…REJ…` | `rejected` — المطالبة مرفوضة |
| أي رقم لا يبدأ بـ `ACC` | غير موجود |

## نقاط النهاية

| الطريقة | المسار | الغرض |
|---|---|---|
| `POST` | `/v1/accident-reports/lookup` | معاينة بالرقم — لا يُخزَّن شيء |
| `POST` | `/v1/accident-reports` | الربط بأمر العمل (+ حدث سجل السيارة + إشعار العميل) |
| `GET` | `/v1/accident-reports?org_id=` | ملفات المنشأة |
| `GET` | `/v1/accident-reports/:id` | التفاصيل + «المتوقع على العميل» |
| `GET` | `/v1/work-orders/:id/accident-report` | ملف الحادث خلف الإصلاح |
| `POST` | `/v1/accident-reports/:id/refresh` | إعادة القراءة من المزوّد (التقييم يصل بعد أيام) |
| `POST` | `/v1/accident-reports/:id/submit-repair` | FR-WO-10 — تسجيل تقرير الإصلاح |

## الأحداث

`AccidentReportLinked` · `AccidentReportUpdated` · `AccidentRepairReported` — عبر الـ outbox، وقوالب الإشعارات
`accident.linked` / `accident.updated` (عربي أولاً، بلا مصطلحات تقنية).

## ما تبقّى قبل التشغيل الحقيقي

- تأكيد الجهة (نجم/تقدير/منجز) وواجهتها، ثم كتابة `monjez.adapter.ts` مقابل نفس المنفذ.
- آلية تفويض العميل للاستعلام إن طُلبت.
- ربط صور الفحص عند التسليم بملف المطالبة إن سمح المزوّد برفع مرفقات.
