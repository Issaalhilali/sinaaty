## التشغيل

```bash
# ارفع حدّ الطلبات لأن كل الحمل يأتي من عنوان واحد، ثم شغّل
THROTTLE_LIMIT=1000000 JOBS_ENABLED=false pnpm --filter api start

k6 run -e BASE_URL=http://localhost:3000/v1 -e VUS=20 infra/load/k6/work-orders.js
k6 run -e BASE_URL=http://localhost:3000/v1 -e VUS=20 infra/load/k6/bidding.js
```

> **الدرس الأول من هذا الاختبار**: أول تشغيل أظهر 99.9% فشلاً — لأن الحدّ الافتراضي (120 طلب/دقيقة لكل عنوان) كان
> يعمل كما يجب. الحدّ ليس عيباً يُلتف عليه في الإنتاج؛ يُرفع في بيئة الاختبار فقط.

## عتبات مدمجة في السكربتات (يفشل التشغيل إن تُخطّيت)

- نسبة الفشل < 1%.
- إنشاء أمر عمل p95 < 800ms · الانتقالات p95 < 500ms · القراءة p95 < 400–500ms.
- الدورة الكاملة p95 < 3 ثوانٍ.

## عندما يبطؤ النظام

1. **أين البطء؟** لوحة Grafana → مدة الطلب حسب المسار، ثم آثار OpenTelemetry (تشمل استعلامات Prisma).
2. **الدفتر والـ outbox**: عمق الـ outbox المتزايد يعني أن معالجاً خارجياً يبطئ، لا أن الـ API بطيء.
3. **قفل الصفوف**: ترقيم الفواتير والسلسلة الضريبية يقفلان صفاً لكل منشأة — بطء هنا يعني ذروة إصدار فواتير، وهو متوقع.
4. **PostGIS**: استعلامات القرب (الورش، السائقون، الموردون) تعتمد فهارس مكانية؛ راجع خطة التنفيذ قبل رفع الأجهزة.

## ما تعلمناه من التشغيلتين اللاغيتين — اختبارا فوضى غير مقصودين (2026-08-21)

في طريقنا إلى soak الساعة أفسدنا تشغيلتين بخطأين في **سكربت الحمل نفسه** — وكلتاهما تحولت إلى
اختبار فوضى حقيقي اجتازه النظام. من يشغّل الإنتاج يحتاج هذه الأرقام بقدر ما يحتاج أرقام الـsoak النظيف:

**العاصفة الأولى (انتهاء الرمز + حلقة بلا مهلة).** رمز الدخول يُصدر في `setup()` وعمره 15 دقيقة؛
عند الدقيقة 15 صار كل طلب 401، ومسار الفشل في السكربت كان يعيد المحاولة بلا مهلة →
**8,000 طلب/ثانية لمدة 45 دقيقة، 29.6M طلباً، 37GB استجابات**. النظام: بقي حياً طوال العاصفة،
المُخنّق حدّ الضرر، تعافى فوراً عند توقفها بلا إعادة تشغيل، والاختلال 0.00 في كل عينة.
الثمن المكشوف: سجل info انتفخ إلى **48GB** (منذها: تشغيلات الحمل بـ`LOG_LEVEL=warn`)، وذروة ذاكرة 1.7GB.

**العاصفة الثانية (إبطال OTP المتبادل).** «إصلاح» التشغيلة الأولى جعل كل VU يعيد تسجيل الدخول دورياً —
متجاهلاً عقد `lib.js` المكتوب: «login من setup فقط، الجميع يتشارك جوال الورشة». عشرة VUs تصادموا
على OTP واحد (كل طلب يبطل رمز غيره) بلا تعافٍ ممكن → **900 تكرار/ثانية، 3.28M طلباً، 95٪ رفض صحيح**.
النظام: فحوصات التدفقات الصحيحة 100/100٪ في نفس الساعة، الاختلال 0.00، طابور الـoutbox مستقر تحت
الفوضى (بفضل تصريف-حتى-الفراغ)، وسجل warn أنهى الساعة بـ**348 بايت**.

**الدروس المثبتة:**
1. عقد `lib.js` يعني ما يقول: لا login أثناء التشغيل. التشغيلات الأطول من TTL الرمز تشغّل الـ API
   بـ`JWT_ACCESS_TTL_SECONDS=7200` — مفتاح بيئة حمل موثق مثل `THROTTLE_LIMIT`؛ الإنتاج يبقى 900.
2. مسار الفشل في سكربت حمل يجب أن **يتمهل مثل مسار النجاح** — فشل بلا مهلة يحوّل أول خطأ عابر إلى عاصفة
   تدفن الأرقام الحقيقية (أُصلح في السكربتين).
3. عمق الـoutbox تحت الحمل كشف أن الموزّع كان مقنّناً بدفعة 50/10 ثوانٍ (300 حدث/دقيقة) بينما الحمل
   يولّد أربعة أضعافها — أُصلح ليصرّف حتى الفراغ كل نبضة، والتهم ركام 15 ألف حدث في <30 ثانية.
   المقاييس الجديدة (`sinaaty_outbox_pending`) أمسكت هذا في **الدقائق الثلاث الأولى** من أول تشغيلة.

100٪. الذاكرة تنفّست 185→233→91MB (ذروة عابرة 422) بلا زحف رتيب؛ طابور الـoutbox متوسطه 199 وذروته

واختلال الدفتر **0.00 في كل عينة**. بيئة الحمل: JWT_ACCESS_TTL_SECONDS=7200، حدود مرفوعة، LOG_LEVEL=warn.
