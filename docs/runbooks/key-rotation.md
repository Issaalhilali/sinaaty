# تدوير المفاتيح والأسرار

## متى

- تسريب مشتبه به (مفتاح في سجلّ، في رسالة، في مستودع).
- مغادرة شخص كان يملك وصولاً للأسرار.
- تدوير دوري: كل 6 أشهر لمفاتيح JWT وأسرار الويب هوك، وسنوياً لمفتاح تشفير البيانات.

## الأسرار وأثر تدويرها

| السر | ماذا يحمي | أثر التدوير | ملاحظة |
|---|---|---|---|
| `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` | جلسات الدخول | كل رموز الوصول تسقط فوراً (15 دقيقة عمرها أصلاً)؛ رموز التحديث تبقى | `pnpm --filter api gen:keys` |
| `PII_ENC_KEY` | الهوية الوطنية، IBAN، شهادات ZATCA | **لا يجوز استبداله وحده** — البيانات الحالية مشفّرة به | يحتاج إعادة تشفير مُدارة؛ لا تُدوّره في حادثة بلا خطة |
| `PSP_WEBHOOK_SECRET` | صحة ويب هوك الدفع | الويب هوكس القديمة تُرفض حتى يُحدَّث لدى المزوّد | نسّق التوقيت مع المزوّد |
| `APPROVAL_LINK_SECRET` | روابط اعتماد العميل | كل الروابط المرسلة تتعطّل | أعد إرسال طلب الاعتماد للعملاء المتأثرين |
| `NAFATH_CALLBACK_SECRET` | مسار نفاذ التجريبي | لا أثر على الإنتاج | التطبيق يرفض الإقلاع بقيمته الافتراضية في الإنتاج |
| `S3_KEY/S3_SECRET` | الوسائط | روابط الرفع الموقّعة القديمة تسقط | |

## الإجراء

1. ولّد السر الجديد (لا تكتبه في تذكرة أو محادثة):
   ```bash
   pnpm --filter api gen:keys                       # مفاتيح Ed25519 لـ JWT
   openssl rand -base64 32                          # سر عام 32 بايت
   ```
2. حدّثه في أسرار العنقود (لا في المستودع)، ثم `helm upgrade`.
3. تحقق من الإقلاع: التطبيق **يرفض** الإقلاع في الإنتاج بأي سر تطويري افتراضي أو مفتاح تشفير أصفار — رسالة الخطأ تسمّي السر.
4. أبطل القديم عند المزوّد (PSP/التخزين) بعد التأكد من نجاح الجديد.
5. اكتب في سجل التدقيق ما دُوِّر ولماذا (بدون قيم).

## بعد تسريب مؤكد

- دوّر السر المتأثر **أولاً**، ثم حقّق.
- ابحث عن الاستخدام: `integration_requests` و`webhook_events` و`audit_log` تُظهر أي طلب تم بالسر القديم.
- إن كان `APPROVAL_LINK_SECRET`: افترض أن أي رابط اعتماد سابق قابل للتزوير — راجع الاعتمادات في نافذة التسريب،
  وتذكّر أن الاعتماد يحتاج **أيضاً** رمز تحقق على جوال العميل (المسار العام لا يُعيد الرمز في الاستجابة، وهذا مثبت باختبار).
