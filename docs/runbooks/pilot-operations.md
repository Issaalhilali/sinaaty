# تشغيل الطيار: المناطق، التهيئة، مفاتيح الميزات، القياس

## 1. المناطق الصناعية (الوحدة التي نقيس بها)

الطيار يُقاس بالمنطقة لا بالمدينة: ورش «الصناعية الثانية» تتبادل القطع فيما بينها، والسطحة بينها دقائق.
المناطق **إعدادات** لا كود:

```bash
curl "$API/v1/admin/pilot/zones" -H "authorization: Bearer $TOKEN"          # القائمة الحالية
curl -X PUT "$API/v1/admin/pilot/zones" -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{"reason_ar":"إضافة منطقة الخرج","zones":[ ... ]}'
curl -X POST "$API/v1/admin/pilot/zones/backfill" -H "authorization: Bearer $TOKEN"   # وسم المواقع القديمة
```

- كل موقع جديد **يُوسم تلقائياً** بالمنطقة التي تقع بداخلها إحداثياته — لا أحد يكتب اسم المنطقة يدوياً.
- المنطقة تُخزَّن بالرمز (`RUH-IND-2`) لا بالاسم؛ التجميع على نص يكتبه البشر لا ينجو من طيار.
- `backfill` يعالج المواقع بلا منطقة **وكذلك** المواقع التي تحمل نصاً قديماً غير مطابق لأي رمز.
- ورشة خارج كل المناطق ليست خطأ — هي ببساطة خارج الطيار.

## 2. تهيئة الورش (Onboarding)

عشر دقائق مع صاحب الورشة تتحول إلى حساب فعّال:

```bash
node apps/api/tools/onboard-pilot.mjs --template > pilot.json   # املأ الملف مع الفريق الميداني
node apps/api/tools/onboard-pilot.mjs pilot.json --dry-run      # ماذا سيحدث
node apps/api/tools/onboard-pilot.mjs pilot.json                # التنفيذ + تقرير JSON
```

ينشئ: المالك (بجواله) → المنشأة (بالسجل التجاري) → الموقع الرئيسي (+ المنطقة من الإحداثيات) → التخصصات →
الاشتراك → عضوية المالك، ثم يكتب سطر تدقيق **مربوطاً بسلسلة التجزئة** باسم من اعتمد التهيئة وسببها.

- **مُتعادِل**: إعادة التشغيل بعد تصحيح تُحدِّث نفس المنشأة (المفتاح: السجل التجاري).
- `reason_ar` إلزامي — التفعيل قرار شخص، لا سطر في ملف.
- المعتمِد يجب أن يملك حساباً بصلاحية منصة (`pnpm --filter api grant:role`).

## 3. مفاتيح الميزات

مفتاح غير موجود = **مغلق**. أي كود جديد يبقى خاملاً حتى يفتحه التشغيل:

```bash
curl "$API/v1/admin/pilot/flags" -H "authorization: Bearer $TOKEN"
curl -X PUT "$API/v1/admin/pilot/flags/group_buys" -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"enabled":false,"zones":["RUH-IND-2"],"reason_ar":"كثافة كافية في الصناعية الثانية"}'
```

| الشكل | المعنى |
|---|---|
| `{"enabled":true}` | للجميع |
| `{"orgs":["<uuid>"]}` | لمنشآت محددة (مجموعة الطيار) |
| `{"org_types":["parts_distributor"]}` | لنوع منشأة |
| `{"zones":["RUH-IND-2"]}` | لمنطقة |
| `{"pct":30}` | لثلاثين بالمئة، ثابتة لكل منشأة (لا تتذبذب بين الطلبات) |

- التطبيقات تقرأ `GET /v1/config` وتُخفي ما ليس مفعّلاً، **والـ API يرفض أيضاً** — الإخفاء وحده ليس مفتاح ميزة.
- كل تغيير يحتاج سبباً مكتوباً ويُسجَّل في `audit_log`.
- `voice_to_invoice` و`ai_inspection` مغلقة في كل مكان لأنها لم تُبنَ بعد (الخطوتان 27 و28) — والتطبيق يتلقى «مغلق» صريحاً لا صمتاً.

## 4. القياس

```bash
curl "$API/v1/admin/pilot/funnel?zone=RUH-IND-2" -H "authorization: Bearer $TOKEN"
curl "$API/v1/admin/pilot/by-zone" -H "authorization: Bearer $TOKEN"
curl "$API/v1/admin/pilot/activation" -H "authorization: Bearer $TOKEN"
```

- **القمع**: أمر عمل → اعتماد العميل → فاتورة → دفع، مع نسب التحويل بينها. هذا ما يُحكم به على الطيار.
- **التفعيل**: كم منشأة من التي هُيّئت استخدمت المنتج فعلاً في النافذة — الرقم الذي يكشف التهيئة الشكلية.
- **حسب المنطقة**: منشآت نشطة، أوامر، فواتير مدفوعة، وإجمالي المدفوع.
- الورشة ترى قمعها هي عبر `GET /v1/pilot/funnel?org_id=…` — نفس الأرقام، مقصورة عليها.

**ما لا يدخل هذا التدفق إطلاقاً**: أسماء، أرقام جوال، هويات. الصفوف تحمل معرّف المنشأة والكيان والمبالغ فقط،
والحدث الواحد يُحتسب مرة واحدة حتى لو أُعيد إرساله من الـ outbox.
