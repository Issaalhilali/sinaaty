# النسخ الاحتياطي والاستعادة

## الأعراض

- حذف أو تعديل خاطئ واسع (سكربت، ترحيل، أو خطأ بشري).
- تلف قاعدة البيانات أو فقد المزوّد.
- تمرين دوري (مطلوب **شهرياً** قبل الإطلاق، ثم ربع سنوي).

## ما لدينا

| الطبقة | المصدر | الاحتفاظ | من يشغّلها |
|---|---|---|---|
| نسخة منطقية (`pg_dump` مخصّص) | `apps/api/tools/backup-restore-drill.sh` | حسب سياسة التخزين | نحن |
| PITR (استعادة لنقطة زمنية) | Supabase Managed Postgres | حسب الخطة | المزوّد |
| أرشيف فواتير ZATCA | `invoices.zatca_xml` داخل نفس القاعدة | 6 سنوات (إلزام ZATCA) | نحن |

> الأرشيف الضريبي داخل القاعدة نفسها اليوم — أي استعادة تشمله. نقله إلى تخزين بارد مسجَّل في `docs/backlog.md`.

## تمرين الاستعادة (المسار الذي نملكه)

```bash
apps/api/tools/backup-restore-drill.sh
```

يأخذ نسخة حقيقية، يستعيدها في قاعدة منفصلة، ثم **يثبت أن النسخة صالحة للعمل** لا موجودة فقط:

1. تطابق عدد الصفوف في الجداول التي لا يجوز أن تفقد صفاً (أوامر العمل، النسخ الموقّعة، التوقيعات، الفواتير، الدفعات،
   الضمان، الدفتر، السندات، المخالصات، سجل التدقيق، طلبات القطع، الضمانات، تقارير الحوادث).
2. الدفتر المزدوج ما زال متوازناً **إلى الهللة**، ولا يوجد قيد غير متوازن.
3. جداول «الإضافة فقط» ما زالت ترفض `UPDATE` في النسخة المستعادة — تُختبر بالسلوك لا بأسماء المشغّلات.

آخر تشغيل ناجح (2026-08-20، بيئة التطوير): نسخة 9.1MB، 3169 أمر عمل و19324 سطر تدقيق، اختلال الدفتر `0.00`،
والأربعة جداول رفضت التعديل. **ملاحظة تشغيلية:** `pg_dump` يجب أن يطابق إصدار الخادم — السكربت يختار العميل المطابق
تلقائياً من Homebrew، ويفشل برسالة واضحة إن لم يجده.

للاحتفاظ بالنسخة والقاعدة بعد التمرين للفحص اليدوي:

```bash
KEEP=1 apps/api/tools/backup-restore-drill.sh
```

## PITR (لم يُجرَّب من جهاز التطوير)

استعادة نقطة زمنية تتم من لوحة Supabase وتحتاج صلاحيات المشروع. الخطوات المتوقعة:

1. أوقف الكتابة: أوقف نسخ الـ API (`replicas=0` في Helm) حتى لا تكتب فوق البيانات المستعادة.
2. من لوحة المشروع → Database → Backups → Point in time → اختر اللحظة **قبل** الحادثة بدقيقة.
3. الاستعادة تُنشئ قاعدة/مشروعاً جديداً — لا تُوجّه الإنتاج إليه قبل التحقق.
4. شغّل التحقق على النسخة المستعادة قبل التبديل:
   ```bash
   DATABASE_URL="<restored-url>" apps/api/tools/backup-restore-drill.sh
   ```
   (سيأخذ نسخة من المستعادة ويتحقق منها بنفس الفحوص الثلاثة.)
5. بدّل `DATABASE_URL` في أسرار العنقود، ثم `helm upgrade` (يشغّل ترحيلات ما قبل الترقية)، ثم أعد النسخ.
6. بعد التبديل: راجع `/v1/admin/ledger/health` و`/v1/admin/outbox` — أحداث ما بعد نقطة الاستعادة **فُقدت**، وقد تحتاج
   إعادة إرسال (انظر [عطل تكامل خارجي](./integration-outage.md)).

> هذه الخطوات مكتوبة من وثائق المزوّد ولم تُنفَّذ فعلياً بعد. **قبل الإطلاق**: نفّذها مرة على مشروع اختبار وسجّل الزمن الفعلي هنا.

## كيف تتأكد أنك أصلحت

- `apps/api/tools/backup-restore-drill.sh` ينتهي بـ `✓ drill passed`.
- `GET /v1/admin/ledger/health` يعيد اختلالاً `0.00`.
- عيّنة يدوية: افتح آخر ثلاث فواتير وتحقق أن أرقامها متسلسلة بلا فجوة (الترقيم لكل منشأة بلا فجوات — أي فجوة تعني فقد صفوف).
